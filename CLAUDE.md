# MPC (pickleball scheduling site)

A single-file page, `index.html`, plus a small server in `api/`, hosted on Vercel at https://mcppikol.vercel.app/ (the GitHub repo is the source; Vercel redeploys on every push to `main`). It handles account sign-up and log in, roles, a session schedule with sign-ups and waitlists, court booking, session editing, and admin menus.

The older Claude Artifact copy (https://claude.ai/artifact/HkcE3XFhhgEVB3Xn9BdF22) is retired: `index.html` now needs `/api/*`, so it only works on the Vercel site (or the local dev server). Do not republish it to the artifact unless the owner asks.

## Push workflow

- Edits stay local until the owner says "push" (or "publish", "deploy", "update the site").
- On "push": commit the changed files (`git add -A`, but never the git-ignored `migration/` folder; a short commit message describing the change, ending with the Co-Authored-By line from the attribution reminder) and run `git push origin main`. Vercel then builds and deploys by itself; report the URL https://mcppikol.vercel.app/ and that the deploy was triggered (it takes under a minute; check the Vercel dashboard if it does not appear). If the git push fails (sign-in expired, or the remote has new commits: `git pull --rebase origin main` first), say so. Never force-push. Git sign-in cannot be done from the background shell, so run `git push` in the user's Terminal panel if it asks for a login.
- Never push without being asked.
- Test locally with `node scripts/dev-server.js 3100` (in-memory data unless the Supabase variables are set; set `OWNER_EMAIL` to try the Super Admin sign-up).

## Hosting setup (Vercel + Supabase)

The database is Supabase (Postgres). The site's server talks to it with the secret service key; the browser never does.

1. Create a Supabase project (free plan is fine; pick a region near the players). Then Dashboard, SQL Editor, New query: paste the whole of `supabase/setup.sql` and Run. It creates the tables `docs` and `counters`, turns row-level security on with no public access, and adds two helper functions. Safe to run again.
2. Environment variables (Vercel project, Settings, Environment Variables, Production; redeploy after changing them):
   - `SUPABASE_URL`: Supabase, Project Settings, API, Project URL (`https://xxxx.supabase.co`).
   - `SUPABASE_SERVICE_ROLE_KEY`: the secret key from the same page (the "service_role" key, not the anon/publishable one). It bypasses row-level security, so it must only ever live in Vercel and never in the page or in git.
   - `AUTH_SECRET`: a random string of 32 or more characters that signs login tokens. Generate one with `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`. Changing it logs everyone out.
   - `OWNER_EMAIL`: the email that becomes Super Admin when it signs up and no Super Admin exists yet (a comma-separated list is allowed). Not needed if the Super Admin account is imported.
   - `APP_TIMEZONE` (optional, default `Asia/Manila`): the time zone session and booking times are in. The server uses it only to decide when a session or booking has ended.
   - `ALLOW_ADMIN_SELF_RESET` (optional, default off): set to `yes` to let Admin and Super Admin accounts use "Forgot password?". Leave it off unless someone is locked out. Email sending (`EMAIL_FROM` with `RESEND_API_KEY` or `BREVO_API_KEY`, optional `SITE_URL`) is built but not used by the current reset flow.
   - `SUPABASE_PUBLISHABLE_KEY`: the publishable (anon) key. Safe to expose: the page uses it only to listen for Realtime "something changed" pings (no data travels in them).
   - Phone push (optional; see "Phone push setup" below): `FIREBASE_SERVICE_ACCOUNT` (server only: the service-account JSON, pasted whole or base64), `FIREBASE_WEB_CONFIG` (the Firebase web app config as one line of JSON) and `FIREBASE_VAPID_KEY` (the web push key pair's public key).
3. First-time data move from the Artifact: the old data was exported into the git-ignored `migration/` folder (accounts, password hashes, roles including the Super Admin, role access, options, booking settings, the session and the sign-ups). With `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` set in the shell, run `node scripts/import-data.js` once (it keeps anything already there; `--replace` overwrites). After that the existing accounts log in with their old passwords and keep their roles.
4. Vercel deploys from GitHub `main`, but only for commits whose author email belongs to the Vercel account (this repo's local git email is keitheta16@gmail.com). Other authors show "Deployment was blocked" on the commit.
5. Supabase free projects pause after about a week without use; resume from the dashboard if the site starts failing with "The database did not accept that".
6. Realtime: in Supabase, Project Settings, Realtime settings, make sure "Allow public access" is on (the pings use the public channel `mpc-sync`). Without it the site still works, but pages only refresh every 6 seconds.
7. GCash details: sign in as a role with Payment settings (Super Admin and Admin by default), open Payments, press Payment settings, and enter the GCash number, account name and QR code. Until then players see "Payments are not set up yet". The QR and receipts are stored in a private Supabase Storage bucket, `payment-assets`, which the server creates by itself on the first upload.

### Phone push setup (Firebase Cloud Messaging)
Needed only for notifications outside the site. In-app notifications and pop-ups work without it.
1. Create a Firebase project (free), then add a Web app. Copy its config object into `FIREBASE_WEB_CONFIG` as one line of JSON.
2. Project settings, Cloud Messaging, Web configuration: generate a Web Push key pair; its public key is `FIREBASE_VAPID_KEY`.
3. Project settings, Service accounts, Generate new private key: paste the downloaded JSON into `FIREBASE_SERVICE_ACCOUNT` (keep it out of git and chat). The server signs its own Google token with it, so no Firebase library is installed.
4. Redeploy. Each person then turns it on in Profile, Notifications. iPhones only receive web push when the site is added to the Home Screen (the page has a manifest and icon for that).

## How it works

## How it works

- Everything lives in `index.html` (HTML, CSS and JS together). The only external resource is the Google Fonts stylesheet.
- Shared data lives in Supabase behind two Vercel functions: `api/auth.js` (sign-up, log in, reset, change password) and `api/data.js` (read everything / write one document). `api/_lib.js` holds the shared code (Supabase over its REST API with plain `fetch`, password hashing, tokens, the permission table). The storage layer still speaks a few Redis-style commands (HGET, HSET, HSETNX, HDEL, HGETALL) that `sbRun` turns into REST calls, so a different store only means replacing that one function. The page uses a small client (`makeDb` in `index.html`) with the same shape the Artifact database had (`collection().onSnapshot / add`, `doc().get / set / update / delete / acquire / onSnapshot`); it asks `/api/data?rev=N` every 6 seconds while the tab is visible (and right after each of its own writes), and the server answers `{ same: true }` when nothing changed. Layout: table `docs(col, id, data jsonb)` holds every document (collections sessions, signups, members, roles, bookings, config, logins); table `counters` holds the change counter (`rev`, bumped on every write) and the login rate limits.
- **Accounts are keyed by email.** The account id (`state.me`) is the first 32 hex characters of SHA-256 of `'kitchen-line:' + lowercased email`, computed by the server (`emailId` in `api/_lib.js`). The literal `'kitchen-line:'` must never change. The logged-in id is kept in localStorage as `kl-acct`, the email as `kl-email` (only used to change the password), and the signed login token as `kl-token`.

- Branding: the business name is MPC. The logo (the supplied artwork, resized to 480px) is embedded once as the `--logo` CSS variable and shown in the header on a white rounded tile (`.logo`). Fonts are Montserrat (headings; the `MPC` wordmark is 800 italic) and Inter (body), plus IBM Plex Mono for small labels. Colours come from the logo: navy `--band`, royal blue `--accent`, yellow `--ball`; dark mode has its own navy palette. The text `'kitchen-line:'` in `emailId()` is the site's old name and must stay, because every account id is a hash that includes it.
- Layout: `.wrap` fills the screen width (capped at 1920px) with side padding of `clamp(16px, 3vw, 48px)`; the top bar, header, filters and session cards all sit inside it so their left and right edges line up.
- Navigation: a top bar in the header has the three-line menu (Dashboard = the session schedule, Profile, Users = member management, Role access; Users and Role access only when the role allows it), a yellow "Book a Court" button beside it, and at the top right the signed-in name, role and a Log out button. "Add new session" and "Session Configurations" are not in the menu: they are two small buttons (`#dash-add`, `#dash-config`, styled like the Configure button on Book a Court) on the right of the Dashboard heading. Each shows only for roles that may use it (`host`, `options`). The new-session form is hidden until "Add new session" is pressed, and Session Configurations opens a dialog over the Dashboard.
- Light and dark mode: the page is **dark by default** (the head script sets `data-theme="dark"` before the first paint unless `kl-theme` holds a saved `light`; the device setting is not consulted). A round sun/moon button (`#theme-btn`, `themeButton`, `toggleTheme`) sits at the far right of the top bar, after Log out; it sets `data-theme="light"` or `"dark"` on `<html>` and keeps the choice in localStorage as `kl-theme` (a tiny script in `<head>` applies it before the first paint, so there is no flash). The button only shows when logged in. Top bar (`renderBar`): Menu, Book a Court and, to its right, the player's **Refundable Balance** chip (`refundChip`, `#rf-chip`, `#rf-slot`; roles that can book) on the left; the signed-in name and role, Log out and the theme button on the right. Tapping the chip opens a compact pop-up (`#rfinfo`, `openRfInfo`/`renderRfInfo`): refundable amount, refund balance and the saved GCash details (name, number, QR), with an **Edit GCash Details** button that opens a separate pop-up (`#rfedit`, `openRfEdit`/`renderRfEdit`, stacked on top). The same pop-up opens from Profile and from the refund choice. It never redirects to Profile. Up to 640px wide the account area drops to its own second row (Log out and theme), and up to 460px the name and role are hidden (they are on the Profile page); it was checked at 335 to 700px with no overlap and no sideways scroll.
- Footer: one centered line, "Copyright © 2026. KitCraft All Rights Reserved." (the old tips about time zones and court size were removed).
- Session choices are not fixed: the lists for level, format, court number and venue live in `config/options` and are managed on the "Session Configurations" page (below). Defaults (`DEFAULT_OPTIONS`): levels Open play, Beginner 2.0–2.5, Intermediate 3.0–3.5, Advanced 4.0+; formats Open play, Ladder, Clinic, Round robin; courts and venues empty. Sessions saved before the rename have level "All levels"; `lvl()` shows and filters those as "Open play". When adding or editing a session, an empty name, court or venue is saved as "-" (day and start time are still required, and an empty capacity falls back to 12).
- Destructive actions use the `--danger` red (`.link.danger`, lighter in dark mode): the second step of removing a player from a session shows "Tap again to remove" in bold red, and reverts after 4 seconds if not confirmed.
- Joining rules (`join`, `myActiveSession`, page-enforced like the other rules): once someone joins a session, including the waitlist, they cannot leave it (there is no Leave button) until it ends and is deleted, and they cannot join another session while they are in an upcoming one (the other cards' Join buttons are disabled with a note). Join also tidies `signups` entries for sessions that no longer exist. Consequence: someone on a waitlist stays locked to that session until it ends. The only way out earlier is an admin using the `moveplayers` permission below.
- Remove or move players: the `moveplayers` feature ("Remove or move players" in Role access; on by default for admin, off for staff and player, super admin always). Roles with it see Move and Remove next to every player, including the waitlist, in the View players pop-up. Remove asks for a second tap (red "Tap again to remove"). Move opens a list of the other upcoming sessions (marked "full, waitlist" when full); the player goes to the end of that session's queue (new join time) and is no longer in the old one. Both rewrite that person's `signups/{id}` (`changeSignups`). Moving never breaks the one-session rule, because the player leaves the old session in the same write.
- Session Configurations (a dialog, `#sesscfg`, opened by the "Session Configurations" button on the Dashboard; `openSessCfg`, `renderSessCfg`, `saveSessCfg`) for roles with the `options` feature (on by default for admin and staff; super admin always; can be changed in Role access). It is built like the Court booking configuration dialog (same panel, sections, and Cancel / Save settings buttons): changes are a draft that is only saved by Save settings, and Cancel, the × and Escape throw them away. One section per list (Level, Format, Court number, Venue), each with removable chips, a one-line Add box, and Reset (or Clear for courts and venues). Levels and formats must keep at least one entry. When courts or venues exist, the add and edit session forms show them as a list (with "-" for none); with none, people type them. Removing an option never changes existing sessions, and the filters still list any level or format an existing session uses. The venue list is shared with court booking.
- Session time is "Set Time": a start and an end time (add form and edit card). The end must be later than the start, on the same day (inline error "The end time must be later than the start time."). Sessions are still stored as `start` plus `duration` in minutes (end minus start); in the add form, moving the start past the end pushes the end to 90 minutes later. On edit, if the start and end are left as they were, the saved duration is kept, so an older session that runs past midnight can still be edited. There is no longer a list of fixed lengths.
- Court booking (`renderBooking`, `confirmBooking`, `/api/pay` action `book`): a yellow "Book a Court" button beside the Menu button (just "Book" on a narrow phone) opens the booking page: a date picker (today up to 90 days ahead), a legend, and a grid with one row per open hour and one column per court, each court labelled with its venue underneath. The **Refundable balance** (top bar chip, not on this page any more) shows what the player would get back if their paid, upcoming bookings were cancelled now (`refundableBalance`: amount actually paid times the refund policy for how long before the hour starts). Cell states: available (green, price), selected (blue), booked by someone else (red; the player's name for roles with View Bookers), yours and confirmed (outlined "Yours"), yours and waiting (dashed amber: "Pay now" while held, "Pending" while staff verify), and unavailable (hatched: started, no rate, or a session on that court). The server prices every hour itself. **Flow:** Confirm booking holds the hours for 15 minutes (`book`, status `hold`), the checkout dialog shows the exact amount, the GCash number, account name and QR, the player pays in GCash, enters the reference number and uploads the receipt (`pay`, status `pending`, payment `pending_verification`), and a thank-you pop-up appears. If the player has refund balance the checkout also offers **Use Refund Balance** (see Refund balance below), and everything paid by GCash needs both the reference number and the receipt screenshot (the page and the server both refuse a payment missing either; the payment stays **Pending Verification** until staff approve it). Closing the checkout keeps the hold; "Cancel booking" releases it; a hold that runs out frees the hours. Staff approve in Payments and only then is the booking `confirmed`. **Two-way conflicts:** a booking cannot take a court that a session uses (same date, venue, court number, overlapping time), and a session cannot be created or moved onto a court that is booked, held, pending or confirmed. Both are checked in the page and again on the server, with a second look after writing to catch simultaneous requests. A player can cancel their own confirmed booking before it starts (see Manage booking); roles with Manage Bookings can cancel anyone's. The "Book courts" permission (`book`) is on for every role by default.
- Three separate booking permissions (all on for admin and super admin by default, off for staff and player, changeable per role in Role access): `bookconfig` "Court Booking Configuration" (manage booking times, courts, venues and hourly rates), `managebookings` "Manage Bookings" (edit or cancel users' bookings), and `viewbookers` "View Bookers" (see the names of players who booked each court). They do not depend on each other: without View Bookers, booked cells and the manage dialog never show a name; without Manage Bookings, booked cells are not clickable.
- Court booking configuration: the "Configure" button on the right of the Book a Court heading (`bookconfig`) opens a dialog (`openBookCfg`, `renderBookCfg`, `saveBookCfg`) to set the open time slots (tap hours 12 AM to 11 PM; each slot is one hour from its start; default 7 AM to 9 PM), the hourly rates (bands of from hour, to hour and a whole-peso price per court per hour; default 200 for 7 AM to 5 PM and 300 for 5 PM to 10 PM), the venues (shared with the session forms, `config/options.venues`) and the courts, each with a venue or "No venue". Until courts are saved, the columns are the court names from Session Configurations (or Court 1 to 4) repeated for every venue (`bookingColumns`). Saving checks that at least one hour is open and one court exists, that each court's venue is in the venue list, that each rate ends after it starts and has a price, that rates do not overlap, and that every open hour has a rate. Settings are stored in `config/booking` (`hours`, `rates`, `courts`) and apply immediately. Existing bookings keep the price they were made at. The court list here is separate from the court names offered when adding a session.
- Manage Bookings button (beside Configure on the Book a Court page, shown to roles with `managebookings`; `openBkList`, `renderBkList`): opens a list dialog of every upcoming booking grouped by reference, with a search box (reference, court, venue and date; also the booker's name for roles with View Bookers), an optional single-date filter and a Manage button per row that opens the Manage booking dialog on top of the list (Escape closes the top dialog first). The list updates live, so a cancelled booking disappears from it.
- Upcoming Bookings (`bookingCard`, under the grid): one card per booking with the date, reference, status chip, amount, a line per court run (court, venue, time, hours), how it was paid, and buttons. Confirmed and not started: **Reschedule** and **Cancel Booking**, side by side. Waiting for payment: Pay now / Send a new receipt and Cancel (releases the hold). Waiting for verification: Details.
- Manage booking dialog (`openManage`, `renderManage`): opened by Reschedule or Details, or by clicking a booked cell. Players can open their own bookings; roles with Manage Bookings can open anyone's. Each court hour is a compact row (court, venue, date, time, status, amount paid) with **Reschedule** and **Cancel Booking** (or **Cancel hour** when the booking has several hours) side by side. **Reschedule** moves one confirmed hour (`reschedule`): same price or lower moves at once and keeps what was paid; a higher price asks the player to pay the difference by GCash first (checkout, `kind: reschedule`), the new hour is held as `resched` and the original stays exactly as it was until staff approve (denied: the new hour is released, nothing else changes). Staff cannot move to a dearer hour for someone (the player pays). **Cancel** (`cancel`, `startCancelFlow`): a player can cancel their OWN booking if it is confirmed and has not started (the server refuses someone else's, held, pending and started hours); roles with Manage Bookings can cancel anyone's (with an inline confirmation). A player cancelling sees the refund policy result first, then cancels, then picks what to do with the refund (below). Hours with a pending reschedule or payment verification cannot be cancelled until that is approved or denied.
- Editing a session: the "Edit" link on a card opens an "Edit session" dialog (`#editdlg`, `renderEditDialog`, `editFields`) instead of turning the card into a form. It has Cancel and Save changes; Escape and the × close it without saving, clicking outside does not (so typing is not lost); keyboard focus stays inside; and it is only rebuilt when something it shows changes, so live updates do not disturb typing. The same time and past-date rules apply. If the session is removed while someone is editing it, the dialog closes with a message.
- The join button on a card is labelled "Join" ("Join waitlist" when the session is full).
- Removing a session: the "Remove session" link on a card opens a confirmation dialog (`#confirm`, `renderConfirm`) asking "Remove this session?", with how many players will be taken out, and the buttons "No, cancel" (focused first) and "Yes, remove". Nothing is deleted until "Yes, remove"; Escape, clicking outside and "No, cancel" all close it. Removing a user (Users page, super admin only) opens a similar dialog (`#confirmuser`, `renderConfirmUser`, `askRemoveUser`) titled "Remove <name>?" with the buttons "No" (focused first) and "Yes"; nothing is deleted until "Yes", and Escape, clicking outside and "No" all close it. Removing a player from a session still uses the two-tap red "Tap again to remove".
- A session cannot be created, or moved, into the past: adding or editing shows an inline error ("That date and time have already passed. Pick a start time in the future.") when the start (`isPast`, local clock) is earlier than now. This applies to every role that can add or edit sessions. When editing, the check runs only if the date or start time was changed, so a session that is already running can still have its name, court or venue fixed. Like the other role checks it is enforced by the page, not the server.
- Session cards on the Dashboard are deliberately minimal: time, title, venue, chips, a "N spots left" line (or "Full · N waitlisted"), and a "View players" button, which is the first item in the card, left-aligned above the time and title. No capacity bars, no "x of y" count, no names on the card. "View players" opens a pop-up (`#modal`, `renderModal`) with the session's title and time, the numbered players, and the waitlist below; it closes with the × or Close button, Escape, or a click outside, keeps keyboard focus inside while open, and updates live. Roles without the `roster` feature see no button.
- The Dashboard shows a calendar icon button (`renderCalendar`) with a status line beside it (how many sessions are upcoming, or scheduled on the picked date). Clicking the icon opens a month date picker as a popover: a dot marks days with sessions, past days are disabled, the arrows move through the next 12 months, and picking a day closes it and filters the list to that date (pick it again, or use "Show all upcoming", to clear). It also closes on Escape or a click outside. An empty day shows "No sessions on this day" with, for roles that can host, "Add a session for this day" (prefills the form date). The Level, Format and "Only my sessions" filters still apply to the dots and counts.
- Profile page (every logged-in user, `renderProfile`): full name and email shown read-only, an optional level rating (2.0 to 5.0+ in half steps, saved as `members/{id}.rating`, cleared by choosing "Not set", shown to admins on the Users page), and "Reset password", which asks for the current password plus a new one twice. The email is not in the database: it is the one typed at log in or sign-up and is kept only in this browser (`kl-email` in localStorage, next to `kl-acct`). A saved login without `kl-email` (from before this existed) is dropped so the person logs in once more. It also holds **GCash refund details** (number, account name, static QR code; all three needed before a GCash refund can be requested; `renderProfileRefunds`, `refund-account`), the **refund balance**, the player's **Refund History** (amount, method, the actual amount refunded, the GCash reference and the refund receipt image, plus the choose-GCash-or-balance buttons for a new refund) and a short balance history.
- Pop-ups share one compact layout (`dlgStatus`): a round icon, a short title, one line of text, a small details card (reference, amount, method, status) and full-width buttons; used for the thank-you after booking, payment approved / not approved, booking cancelled (with a Choose now button), refund added to balance and Payment Refunded (with the receipt thumbnail). Dialog and form padding, gaps and button sizes were tightened across the site, and the checkout, profile and staff cards were checked at 360px and 375px wide.
- Screens when logged out: Log in (email and password, a "Forgot password?" link and a "Sign up" link), Forgot password (email only; "Find my account"), Choose a new password (reached after the account is found, or after an admin reset) and Sign up (name, email, password of 8+ characters, with a "Log in" link). A saved login is dropped if the account was removed or an admin reset its password. Copy is upbeat: the tagline above "MPC" is "Find your court · Meet your crew · Let's play!", the logged-out status line is "Lace up, log in and grab your spot on court!", and loading says "Warming up the courts…".
- Passwords and login tokens: the server stores each password only as a salted PBKDF2-SHA-256 hash (200,000 rounds, email mixed into the input: `email + '\n' + password`, the same recipe the page used before, so old hashes still verify) in `logins/{id}`. That collection is never sent to browsers. A correct log in or sign-up returns a token (`id` and expiry, HMAC-signed with `AUTH_SECRET`, valid 30 days) that must accompany every `/api/data` call; logging out deletes it and reloads the page, and a rejected token (account removed, secret changed) logs the person out. Attempts are rate limited in the database (8 tries per 10 minutes per account and IP for log in, password change and reset; 15 sign-ups per hour per IP).

- Forgot password (self-service, no email): "Forgot password?" on the Log in screen asks for the email and calls `forgot` in `api/auth.js`. The server hashes the email to the account id and looks it up. If it is not found the page says so ("We could not find an account with that email..."). If it is found, the server returns a reset token and the page goes straight to "Choose a new password" (`resetpw`), then logs the person in. The token is signed with `AUTH_SECRET`, holds `t: 'reset'`, the account id, the email (needed to rebuild the password hash; the email is still never stored), a marker of the current password (`logins.setAt`) and a 10-minute expiry. It works once (the marker stops matching after the change), is never accepted as a login token, and the same applies the other way round. Limits: 8 requests per 10 minutes per email and 20 per 10 minutes per IP. **Known trade-off:** nobody proves they own the email, so anyone who knows a player's email can reset that player's password. To limit the damage, Admin and Super Admin accounts are refused ("For safety, admin accounts cannot be reset this way. Ask the Super Admin..."); setting the Vercel variable `ALLOW_ADMIN_SELF_RESET=yes` lifts that for everyone (for example for a locked-out Super Admin, then remove it again). Safer options if this matters later: send the link by email (`sendMail` and the Resend/Brevo code in `api/_lib.js` are kept for that, currently unused), or ask for something only the owner knows.
- Forgot password, by an admin (still available, for people whose email is out of reach): an admin (or super admin) clicks "Reset password" on the Users page, which sets `roles/{id}.pwReset`. The person enters their email on the Log in screen and the server answers "reset", so the page asks for a new password (`setpw`, no old one needed); the flag clears when `members/{id}.pwSetAt` is newer. Until then anyone who knows that email can claim the account. If the Super Admin is locked out and has no working email, set `roles/<id>.pwReset` to the current time in the database (row `col = roles`, `id = <id>` in the `docs` table), then log in with that email and choose a new password.

## Data model (db collections)

- `sessions/{id}`: `title`, `date` (YYYY-MM-DD), `start` (HH:MM), `duration` (minutes), `court`, `venue`, `level`, `format`, `capacity`, `hostId` (an account id), `hostName`, `createdAt`. A session is deleted once its end time (start + duration, in the viewer's local time) passes: any signed-in viewer with write access deletes it on load or within 15 seconds (`purgeEnded` / `clockTick`). Nothing keeps a history of past sessions.
- `members/{id}`: `name`, `createdAt`, `pwSetAt` (the account profile, written at sign-up).
- `logins/{id}`: the password hash, described above.
- No email is stored anywhere. The Users page lists members by name. Do not add a plaintext email field without a way to keep it private.
- `roles/{id}`: `role`, `suspended?`, `owner?`, `pwReset?`, `by`, `at` (written by managers).
- `signups/{id}`: `joined` as `{ sessionId: joinTimestamp }`; the roster and waitlist order come from these timestamps.
- `config/booking`: `hours` (array of start hours, 0 to 23), `rates` (array of `{ from, to, price }`, hours 0 to 24) and `courts` (array of `{ name, venue }`). Missing or invalid values fall back to `DEFAULT_BOOKING`.
- `bookings/{date}_{venue}_{court}_{hour}` (no venue part when there are no venues): `date`, `venue`, `court`, `hour`, `by`, `byName`, `ref` (shared by every hour in one booking, like `MPC-XXXXXX`), `price` (the rate when booked or moved), `paid` (what was actually paid and verified for this hour), `status` (`hold` with `holdUntil`, `pending` with `payId`, `resched` with `payId` and `moveFrom`, `confirmed`; older bookings with no status count as confirmed with nothing paid), `at`. The document id is unique to the slot and is claimed with an insert-if-absent write, so two people can never hold the same hour; expired holds are treated as free and overwritten. Only `/api/pay` creates or changes bookings; the data API only lets anyone tidy an hour that has ended or a hold that ran out. A booking is deleted once its hour has ended (`purgeEnded`).
- `payments/{id}`: `kind` (`booking` or `reschedule`), `bookingRef`, `by`, `byName`, `email` (only if it really belongs to that account), `amount` (the exact amount due, from the server), `gcashRef`, `proofPath`, `status` (`pending_verification`, `paid`, `rejected`), `slots`, `move` (for a reschedule), `reason`, `submittedAt`, `reviewedBy`, `reviewedAt`. `refunds/{id}`: `bookingRef`, `by`, `slots` (each with `paid` and `percent`), `paid`, `refundable`, `policy`, `method` (`gcash` or `balance`, chosen by the player), `acct` (a copy of the player's GCash number, name and QR path), `status` (`awaiting_user`, `requested`, `approved`, `refunded`, `denied`), `actualAmount`, `refundRef`, `receiptPath`, who and when for each step. `notifications/{id}` (id is `event.refId.person`, so each event reaches each person once): `to`, `kind`, `title`, `body`, `data`, `read`, `push` (devices reached or failed). `locks/{key}`: one-time markers (`gcash:<normalised reference>`, `payref:<booking ref>`, `ev:approve:<id>` and so on) that stop duplicate references, approvals, refunds and notifications. `pushtokens/{id}`: a person's registered phone devices (max 5). `config/payment`: `gcashNumber`, `accountName`, `qrPath`, `refundPolicy` (rows of `hours` before and `percent`, default 100% at 48 hours or more, 50% at 24 hours or more, otherwise 0%). All of these except `config/payment` are readable only by the people allowed to see them (see below) and none can be written through the data API.
- `refundaccts/{uid}`: a player's GCash refund details (`number`, `name`, `qrPath` under `refundqr/`); readable only by the player and by roles with Refunds. `balances/{uid}`: `amount`, `reserved`. `ledger/{id}`: `uid`, `type` (`refund-credit`, `booking-use`), `amount` (+/-), `balanceAfter`, `ref`, `at`; own entries only (Refunds staff see all). A payment can also have `total`, `balanceUsed` (the part paid from refund balance), `method: 'balance'` (paid entirely by balance), and then `amount` is only what is due by GCash. None of these are writable through the data API.
- `config/roles`: `defs` as `{ roleKey: { label, perms } }` for the role access table.
- `config/options`: `levels`, `formats`, `courts`, `venues` (arrays of text). An older `durations` key may still be stored; it is ignored. Any key that is missing falls back to `DEFAULT_OPTIONS`.
- The older collections `accounts`, `players`, `contacts` and `data/users/*` (keyed by Claude sign-in, from before email accounts) are no longer read. Their docs can be deleted.

## Roles and permissions

- Built-in roles: super admin (always everything), admin, staff, player. Super admin can add custom roles.
- Features: view, join, roster, host, edit, remove, people, options, moveplayers, book, bookconfig, managebookings, viewbookers, **payments**, **refunds**, **paysettings**. Defaults are in `DEFAULTS` in the script and in `api/_lib.js`; the three new ones are on for admin (and always for super admin) and off for staff and player. `people` opens the Users page (`renderUsers`): overview tiles, member search, role changes, Reset password, pause access, and Remove (super admin only; deletes that account's members, roles, signups and logins docs).
- Role Access page (permission `roleaccess`, on for Admin and Super Admin): admins can open Role access and change what the other roles can do, add and delete custom roles. The **Admin column is locked** for everyone except a Super Admin (the server compares effective Admin permissions and refuses a change with 403), so an admin cannot give Admins more power, lock Admins out, or rename the role. **Only a Super Admin can make someone a Super Admin** (or an Admin): the page offers no such choice to anyone else, and `api/data.js` returns 403 for any other role writing `role: super_admin`, for changing your own role, and for changing the owner account; a `super_admin` entry written into the role table is dropped. A custom role given the `roleaccess` permission can use the page too but still cannot grant Super Admin.
- Super admin: the Super Admin account was imported from the Artifact (`roles/{id}`: `role: super_admin, owner: true`). On a fresh database, the first sign-up with the `OWNER_EMAIL` address becomes Super Admin when none exists; everyone else starts as a player. The owner record cannot be edited through the site.
- Role checks are enforced twice: the page hides what a role cannot use, and `api/data.js` refuses the write (403) using the same table (`DEFAULTS` plus the saved `config/roles`). Server rules, by collection: sessions (add needs host, edit needs edit or being the host, delete needs remove or being the host, and anyone may delete one that has ended; `hostId` is forced to the caller), signups (your own with join, anyone's with moveplayers), members (only your own name and rating; the `createdAt` and `pwSetAt` fields only change through `/api/auth`), roles (needs people; nobody changes their own role or the owner; only a super admin touches admins or creates one; suspended is honoured), config/roles (super admin only), config/options (options or bookconfig), config/booking (bookconfig), bookings and everything involving money (not writable here at all: only /api/pay creates, pays, moves or cancels them; the data API only lets anyone tidy an hour that has ended or a hold that ran out), config/payment (only /api/pay). Reads are filtered per person: payments and refunds only for roles with that permission or the owner, notifications only for their owner, and locks, push tokens and passwords for nobody. A suspended account can read but not write. Not enforced on the server: the one-session-at-a-time rule and the contents of session fields. Prices, holds, conflicts, payments, refunds and notifications are all decided on the server.
- Payments, refunds, notifications, settings (all in `/api/pay`, never the data API):
  - **Payments** menu (`payments`; `renderPayments`): every GCash submission with player name and account details (role, member since, rating, email), booking reference, venue, court, date and time, amount, GCash reference, the receipt image (click to enlarge), submission date and status; filters and search; **Approve** (one click, no second confirmation: the booking becomes Confirmed, the payment Paid, and the player and the staff assigned to that venue are notified once; the button locks while it runs and the server accepts only one approval even if it is clicked many times) and **Deny** (with a reason: the payment is Rejected, the player is told, the hours stay held for 30 minutes so a corrected receipt can be sent, and the reference number can be used again). Nothing is ever approved automatically; two reviewers pressing Approve at once produce one approval. A GCash reference number can only ever be used once.
  - **Refunds** (`refunds`; `renderRefunds`; `cancel`, `refund-choose`, `refund-complete`): a paid hour that is cancelled (by the player or by staff) opens a refund **Awaiting player** with the amount the refund policy gives back (nothing opens if the policy gives nothing). **Nothing is credited or sent until the player chooses, and there is no default.** The choice dialog (`renderCancelFlow`, step `choose`; also reachable from Profile, Refund History, and from the "Choose now" pop-up) has two explicit buttons: **Request GCash Refund** (needs the player's GCash number, name and QR saved in Profile; it becomes a request, status Requested, `method: gcash`, and is never turned into balance) and **Keep as Refund Balance** (`method: balance`; credited immediately, once, through a ledger entry `credit_<refundId>`, status Refunded; it cannot be sent by GCash afterwards). Choosing twice, switching, or two clicks at once are refused (409), so there is never a double credit. For a GCash request, staff press **Process refund** (one step; the old separate approve step is no longer needed but still works): they send the money by hand in GCash, then enter the **amount actually sent, the GCash reference and the receipt screenshot**. All three are mandatory on the page and on the server; only then is the refund marked **Refunded** (`actualAmount`, `refundRef`, `receiptPath`) and the player shown the "Payment Refunded" pop-up. Two staff processing at once produce one refund, and a GCash refund can never create a balance credit (tests check this across every refund). Deny (with a reason) is possible before it is refunded.
  - **Refund balance** (`balances/{id}`: `amount` and `reserved`; every change is also a `ledger` entry): credited the moment the player explicitly chooses "Keep as Refund Balance" for a refund (once; staff have nothing to approve). On the booking checkout a player with balance sees two options, **Pay with GCash** or **Use Refund Balance**. If the balance covers the booking, it is confirmed immediately (no staff check needed since no GCash is involved) and the balance is deducted; if it covers only part, the player pays the rest by GCash (reference number and receipt both required) and the balance part is set aside as `reserved` so it cannot be spent twice. The balance is deducted only when staff approve the payment (the booking is confirmed); a denied payment releases the reservation. Changes to one person's balance are serialised with a short lock, so two bookings at once can never spend more than the balance. The balance shows in Profile (with refund history and balance history), in the Refundable Balance box, and in Your upcoming bookings, which also shows how each booking was paid (balance, GCash or both).
  - **Payment settings** (`paysettings`; button on the Payments page, `renderPayDlg`): GCash number, account name, QR code upload or replacement, and the refund policy rows. Applies to new payments at once. The QR and receipts live in the private `payment-assets` Storage bucket and are served only by `/api/pay?file=...` after a permission check (the QR to any logged-in player, a receipt to its owner or a payments reviewer).
  - **Notifications**: created by the server only when a verified event happens, each once per person (see `notify` in `api/_book.js`). Player-facing ones open a pop-up in the page (payment approved or not approved, rescheduled, booking cancelled, refund completed or denied; the approval pop-up shows the venue, court, time and the reference number to show the venue staff); staff-facing ones (new payment, new refund request, new confirmed booking at your venue) show as a short message. Profile lists the latest ones and has the phone-push switch.
  - **Realtime**: after every write the server sends a Supabase Realtime Broadcast ping (`{ rev }` only) on the public channel `mpc-sync`. Open pages hold one WebSocket (`makeDb`, `connect`), and a ping makes them fetch what they are allowed to see (never the ping itself carrying data, so no Row Level Security policies are needed: the tables stay locked and only the server reads them). While the socket is up the page checks once a minute; if it drops it checks every 6 seconds and reconnects with backoff, and on every (re)join it asks for anything missed using the change counter. The page's own actions also refresh straight away.
  - **Phone push (Firebase)**: Profile has a switch (`enablePush`, `disablePush`). It asks permission, registers `/firebase-messaging-sw.js`, gets a token and stores it with `push/register`. The server sends data-only FCM messages (`pushTo`) after each stored notification, removes expired tokens, records delivery on the notification, and never sends the same event twice. Logging out unregisters that device. Works on Android and on iPhones when the site is on the Home Screen (`manifest.webmanifest`, `icon.jpg`).

## Refund rules and profile layout

- **Refund rules (fixed, replace the old percentage rows; Payment settings no longer has a policy section):** cancelled before the booked start time = full refund, the player chooses GCash or Refundable Balance (`rule: before_start`); cancelled after the start time (until the hour ends) = the amount paid is credited to the Refundable Balance at once, never GCash (`rule: after_start`, `afterStart: true`). Players and staff can both cancel a started, not yet ended hour; an ended hour is refused. `cancel` in `api/pay.js` splits one booking into a before-start and an after-start refund; `creditRefundToBalance` is the single place a balance credit is made (ledger `credit_<refundId>` and lock `ev:rfchoose:<id>` make it once-only); `refund-choose` refuses GCash for `afterStart` refunds. Old refunds keep their stored `policy` array.

## Refundable Balance integrity and the Audit Trail

- **What the Refundable Balance is:** only the stored credit in `balances/{uid}` (the top-bar chip and pop-up show `available` = amount minus reserved). What a player has *paid* for bookings is never part of it; the pop-up shows it separately as "Paid for upcoming bookings". An earlier version of the chip showed "what you would get back if you cancelled" (the sum paid), which looked like a credit: a payment of 700 for three hours appeared as a 700 Refundable Balance. No server code ever credited a payment (checked: only `creditRefundToBalance`, the legacy `refund-approve`, `balance-link`, and the reschedule credit write to a balance).
- **The only ways a balance goes up:** (1) a refund the player keeps as balance, or an after-start cancellation (`creditRefundToBalance`, ledger `credit_<refundId>`); (2) a reschedule to a cheaper hour: only the excess (old paid minus new price) is credited, after the move succeeded, once (ledger `rs_<hash>`, type `resched-credit`), and the moved booking's `paid` becomes the new price; equal price credits nothing; a dearer hour is paid by GCash and credits nothing; (3) `balance-link` between accounts. Every change has a ledger entry, so `sum(ledger) == amount` for each account.
- **Balance check / correction (Super Admin, Audit Trail page):** `balance-check` compares each stored amount with its ledger sum; `balance-fix` sets a mismatching amount back to the ledger sum (needs the amount seen, a reason, and `confirm`; stale views are refused). It changes only the balance number: no payment, refund or ledger record is touched, and it is audited. The live database could not be read from the coding session (the Supabase tool was denied), so the real affected account has to be checked and corrected from this page.
- **Audit Trail** (menu item, Super Admin only; `audit` collection; `#view-audit`): append-only records `{ at, area, action, summary, actor{id,name,role}, subject, refs, before, after, amount, sig }`. Written only by the server through `L.audit()` (never throws): `api/pay.js` records booking, payment, cancel, reschedule, refund, balance and settings actions in `auditPre`/`auditPost` around every action (so a new action needs a case there); `api/data.js` `auditWrite` records sessions, join/leave/move, role and permission changes, suspensions, password-reset flags, option/booking configuration and account removal; `api/auth.js` records signups and password changes. `sig` is an HMAC over the canonical record, so an edit made directly in the database shows as "altered" (the page also shows a count). The data API refuses any read or write of `audit`; `audit-list` (search `q`, `area`, `actor`, `from`/`to`, paging with `before`) is the only reader and needs `w.isSuper`. Logins (sign-ins) are not recorded.
- **Pop-ups and cards:** the payment-approved / rescheduled pop-up shows the reference number prominently, then one block per venue and date with one row per court and time (`approvalDetail`; notification `data.slots`); Upcoming Bookings cards (`bookingCard`) are a grid of cards with a header, aligned court rows, a payment line and full-width buttons.
- **One confirmation per booking:** a booking paid entirely with Refundable Balance no longer opens the client-side "Booking confirmed" thank-you; the server notification (`payment-approved`) is the only pop-up. Its `data` carries `amount`, `paidWith` (Refund Balance, GCash, or both), `status` and `slots`, shown by `approvalDetail`. GCash and combined payments show the "Thank you / Pending Verification" pop-up when submitted and the confirmation only after staff approve (the notification is once per event and person).

## Speed and phones

- **Sessions are faster.** `makeDb.write` shows an accepted set/update/delete at once in the local copy (`patchLocal`), then confirms with a background refresh (never an older answer over a newer one: `j.rev >= rev`); `add` still waits for the refresh. All collections of one refresh redraw once (`renderSoon`). The Dashboard list (`renderList`) only rebuilds when something a card shows changed (`listSig`). Join (`state.joining`), remove/move player (`busyUids`) and Save changes in Edit session (`state.edit.saving`) ignore repeat taps and show "Joining…" / "Saving…"; a failed edit save keeps the dialog open and no longer says "Session updated.". The server read still returns every collection the person may see; narrowing it would need per-collection revisions (not done).
- **Phones:** touch targets are at least 40px at 700px wide and below (or on touch screens), pop-ups use `dvh` so they scroll inside the visible screen and, in landscape (height 520px or less), start at the top. Every page was measured at 320, 375, 414, 568x320, 667x375, 768 and 1024 wide with no sideways overflow.
