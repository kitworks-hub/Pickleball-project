# MPC (pickleball scheduling site)

A single-file page, `index.html`, that runs as a published Claude Artifact. It handles account sign-up and log in, roles, a session schedule with sign-ups and waitlists, session editing, and admin menus.

Published copy: https://claude.ai/artifact/HkcE3XFhhgEVB3Xn9BdF22 (private to the owner until shared from the Share menu). To update it, republish this file to that same URL with the Artifact tool.

## Push workflow

- Edits to `index.html` stay local until the owner says "push" (or "publish", "deploy", "update the site").
- On "push": read the live artifact first if this session has not read or published it, merge any newer live changes, then republish `index.html` to the URL above. Omit `icon`. Omit `capabilities` too, unless the stored declaration differs from the list under "How it works"; in that case pass the full list (a non-empty `capabilities` replaces the whole declaration).
- "Push" also saves to GitHub (repository https://github.com/kitworks-hub/Pickleball-project, branch `main`, remote `origin`). After the artifact publish succeeds, commit `index.html` and `CLAUDE.md` (`git add index.html CLAUDE.md`, a short commit message describing the change, ending with the Co-Authored-By line from the attribution reminder) and run `git push origin main`. Skip the commit if nothing changed. If the git push fails (for example the sign-in expired, or the remote has new commits: `git pull --rebase origin main` first), say so; the live site is already updated. Never force-push. Git sign-in cannot be done from the background shell, so run `git push` in the user's Terminal panel if it asks for a login.
- Never push without being asked. After a push, report the live URL, what changed, and that it was saved to GitHub.
- The page only works on claude.ai, because it relies on the Artifact `db` and `user` capabilities. Hosting it on a custom domain would need a real backend (for example Supabase or Firebase) and a real login service in place of those capabilities.

## How it works

- Everything lives in `index.html` (HTML, CSS and JS together). The only external resource is the Google Fonts stylesheet.
- Shared data uses the Artifact `db` capability. The `user` capability is used only for `isOwner()`, `canEdit()` and `can('data.write')`. There is no separate backend.
- **Accounts are keyed by email, not by Claude sign-in.** The account id (`state.me`) is the first 32 hex characters of SHA-256 of `'kitchen-line:' + lowercased email`. The same email is the same account on any Claude sign-in, and one Claude sign-in can hold many accounts (log out, then sign up with another email). The logged-in id is kept in localStorage as `kl-acct`.
- Capabilities declared when publishing (the declaration changed from the old per-Claude-user rules, so pass it explicitly on the next push):
  - `user: {}`
  - `db: {}` with no rules. Every collection uses the default: signed-in viewers read, Contributors write. (The platform refuses a rule where read needs a higher level than write, so emails cannot be kept admin-only while members write them. Emails are therefore not stored at all.)
- Branding: the business name is MPC. The logo (the supplied artwork, resized to 480px) is embedded once as the `--logo` CSS variable and shown in the header on a white rounded tile (`.logo`). Fonts are Montserrat (headings; the `MPC` wordmark is 800 italic) and Inter (body), plus IBM Plex Mono for small labels. Colours come from the logo: navy `--band`, royal blue `--accent`, yellow `--ball`; dark mode has its own navy palette. The text `'kitchen-line:'` in `emailId()` is the site's old name and must stay, because every account id is a hash that includes it.
- Layout: `.wrap` fills the screen width (capped at 1920px) with side padding of `clamp(16px, 3vw, 48px)`; the top bar, header, filters and session cards all sit inside it so their left and right edges line up.
- Navigation: a top bar in the header has the three-line menu (Dashboard = the session schedule, Profile, Users = member management, Role access; Users and Role access only when the role allows it), a yellow "Book a Court" button beside it, and at the top right the signed-in name, role and a Log out button. "Add new session" and "Session Configurations" are not in the menu: they are two small buttons (`#dash-add`, `#dash-config`, styled like the Configure button on Book a Court) on the right of the Dashboard heading. Each shows only for roles that may use it (`host`, `options`). The new-session form is hidden until "Add new session" is pressed, and Session Configurations opens a dialog over the Dashboard.
- Session choices are not fixed: the lists for level, format, court number and venue live in `config/options` and are managed on the "Session Configurations" page (below). Defaults (`DEFAULT_OPTIONS`): levels Open play, Beginner 2.0–2.5, Intermediate 3.0–3.5, Advanced 4.0+; formats Open play, Ladder, Clinic, Round robin; courts and venues empty. Sessions saved before the rename have level "All levels"; `lvl()` shows and filters those as "Open play". When adding or editing a session, an empty name, court or venue is saved as "-" (day and start time are still required, and an empty capacity falls back to 12).
- Destructive actions use the `--danger` red (`.link.danger`, lighter in dark mode): the second step of removing a session or a user shows "Tap again to remove" in bold red, and reverts after 4 seconds if not confirmed.
- Joining rules (`join`, `myActiveSession`, page-enforced like the other rules): once someone joins a session, including the waitlist, they cannot leave it (there is no Leave button) until it ends and is deleted, and they cannot join another session while they are in an upcoming one (the other cards' Join buttons are disabled with a note). Join also tidies `signups` entries for sessions that no longer exist. Consequence: someone on a waitlist stays locked to that session until it ends. The only way out earlier is an admin using the `moveplayers` permission below.
- Remove or move players: the `moveplayers` feature ("Remove or move players" in Role access; on by default for admin, off for staff and player, super admin always). Roles with it see Move and Remove next to every player, including the waitlist, in the View players pop-up. Remove asks for a second tap (red "Tap again to remove"). Move opens a list of the other upcoming sessions (marked "full, waitlist" when full); the player goes to the end of that session's queue (new join time) and is no longer in the old one. Both rewrite that person's `signups/{id}` (`changeSignups`). Moving never breaks the one-session rule, because the player leaves the old session in the same write.
- Session Configurations (a dialog, `#sesscfg`, opened by the "Session Configurations" button on the Dashboard; `openSessCfg`, `renderSessCfg`, `saveSessCfg`) for roles with the `options` feature (on by default for admin and staff; super admin always; can be changed in Role access). It is built like the Court booking configuration dialog (same panel, sections, and Cancel / Save settings buttons): changes are a draft that is only saved by Save settings, and Cancel, the × and Escape throw them away. One section per list (Level, Format, Court number, Venue), each with removable chips, a one-line Add box, and Reset (or Clear for courts and venues). Levels and formats must keep at least one entry. When courts or venues exist, the add and edit session forms show them as a list (with "-" for none); with none, people type them. Removing an option never changes existing sessions, and the filters still list any level or format an existing session uses. The venue list is shared with court booking.
- Session time is "Set Time": a start and an end time (add form and edit card). The end must be later than the start, on the same day (inline error "The end time must be later than the start time."). Sessions are still stored as `start` plus `duration` in minutes (end minus start); in the add form, moving the start past the end pushes the end to 90 minutes later. On edit, if the start and end are left as they were, the saved duration is kept, so an older session that runs past midnight can still be edited. There is no longer a list of fixed lengths.
- Court booking (`renderBooking`, `confirmBooking`): a yellow "Book a Court" button sits beside the Menu button (just "Book" on a narrow phone) and opens the booking page: a date picker (today up to 90 days ahead, previous/next day, Today), a legend, and a grid with one row per open hour and one column per court. Each court belongs to a venue, and the venue is written as small text beneath the court name in the column header (there is no venue dropdown). Two courts can share a name at different venues; they are separate columns and separate bookings. Cell states: available (green, shows the price), selected (blue), booked by someone else (red; shows "Booked", or the player's name for roles with View Bookers), booked by you (outlined "Yours"), and unavailable (hatched grey: the hour has already started, no rate is set for it, or a session on that date, court and venue is using the court; court names are matched ignoring case and a leading "Court", and a session with no venue blocks every venue). Only available cells can be selected, and everything is re-checked when confirming. The summary lists consecutive hours on a court (with its venue) as one line with its price breakdown, the total, and "Confirm booking", which reserves the hours and shows a reference like MPC-XXXXXX. No payment is taken on the site: the total is the amount due. Players cannot cancel their own bookings; only roles with Manage Bookings can. The "Book courts" permission (`book`) is on for every role by default.
- Three separate booking permissions (all on for admin and super admin by default, off for staff and player, changeable per role in Role access): `bookconfig` "Court Booking Configuration" (manage booking times, courts, venues and hourly rates), `managebookings` "Manage Bookings" (edit or cancel users' bookings), and `viewbookers` "View Bookers" (see the names of players who booked each court). They do not depend on each other: without View Bookers, booked cells and the manage dialog never show a name; without Manage Bookings, booked cells are not clickable.
- Court booking configuration: the "Configure" button on the right of the Book a Court heading (`bookconfig`) opens a dialog (`openBookCfg`, `renderBookCfg`, `saveBookCfg`) to set the open time slots (tap hours 12 AM to 11 PM; each slot is one hour from its start; default 7 AM to 9 PM), the hourly rates (bands of from hour, to hour and a whole-peso price per court per hour; default 200 for 7 AM to 5 PM and 300 for 5 PM to 10 PM), the venues (shared with the session forms, `config/options.venues`) and the courts, each with a venue or "No venue". Until courts are saved, the columns are the court names from Session Configurations (or Court 1 to 4) repeated for every venue (`bookingColumns`). Saving checks that at least one hour is open and one court exists, that each court's venue is in the venue list, that each rate ends after it starts and has a price, that rates do not overlap, and that every open hour has a rate. Settings are stored in `config/booking` (`hours`, `rates`, `courts`) and apply immediately. Existing bookings keep the price they were made at. The court list here is separate from the court names offered when adding a session.
- Manage Bookings button (beside Configure on the Book a Court page, shown to roles with `managebookings`; `openBkList`, `renderBkList`): opens a list dialog of every upcoming booking grouped by reference, with a search box (reference, court, venue and date; also the booker's name for roles with View Bookers), an optional single-date filter and a Manage button per row that opens the Manage booking dialog on top of the list (Escape closes the top dialog first). The list updates live, so a cancelled booking disappears from it.
- Manage bookings (`managebookings`, `openManage`, `renderManage`): roles with it can click any booked cell, including their own, to open "Manage booking" for that booking reference. It lists each court hour with Edit and Cancel hour, and Cancel whole booking. Cancelling asks "No, keep it" / "Yes, cancel ..." first. Edit moves one hour to another date, court (venue) or hour among the free ones; the moved hour keeps the booking reference and booker and takes the current rate for its new hour. Moves claim the new slot first, then delete the old one.
- Editing a session: the "Edit" link on a card opens an "Edit session" dialog (`#editdlg`, `renderEditDialog`, `editFields`) instead of turning the card into a form. It has Cancel and Save changes; Escape and the × close it without saving, clicking outside does not (so typing is not lost); keyboard focus stays inside; and it is only rebuilt when something it shows changes, so live updates do not disturb typing. The same time and past-date rules apply. If the session is removed while someone is editing it, the dialog closes with a message.
- The join button on a card is labelled "Join" ("Join waitlist" when the session is full).
- Removing a session: the "Remove session" link on a card opens a confirmation dialog (`#confirm`, `renderConfirm`) asking "Remove this session?", with how many players will be taken out, and the buttons "No, cancel" (focused first) and "Yes, remove". Nothing is deleted until "Yes, remove"; Escape, clicking outside and "No, cancel" all close it. Removing a user and removing a player from a session still use the two-tap red "Tap again to remove".
- A session cannot be created, or moved, into the past: adding or editing shows an inline error ("That date and time have already passed. Pick a start time in the future.") when the start (`isPast`, local clock) is earlier than now. This applies to every role that can add or edit sessions. When editing, the check runs only if the date or start time was changed, so a session that is already running can still have its name, court or venue fixed. Like the other role checks it is enforced by the page, not the server.
- Session cards on the Dashboard are deliberately minimal: time, title, venue, chips, a "N spots left" line (or "Full · N waitlisted"), and a "View players" button, which is the first item in the card, left-aligned above the time and title. No capacity bars, no "x of y" count, no names on the card. "View players" opens a pop-up (`#modal`, `renderModal`) with the session's title and time, the numbered players, and the waitlist below; it closes with the × or Close button, Escape, or a click outside, keeps keyboard focus inside while open, and updates live. Roles without the `roster` feature see no button.
- The Dashboard shows a calendar icon button (`renderCalendar`) with a status line beside it (how many sessions are upcoming, or scheduled on the picked date). Clicking the icon opens a month date picker as a popover: a dot marks days with sessions, past days are disabled, the arrows move through the next 12 months, and picking a day closes it and filters the list to that date (pick it again, or use "Show all upcoming", to clear). It also closes on Escape or a click outside. An empty day shows "No sessions on this day" with, for roles that can host, "Add a session for this day" (prefills the form date). The Level, Format and "Only my sessions" filters still apply to the dots and counts.
- Profile page (every logged-in user, `renderProfile`): full name and email shown read-only, an optional level rating (2.0 to 5.0+ in half steps, saved as `members/{id}.rating`, cleared by choosing "Not set", shown to admins on the Users page), and "Reset password", which asks for the current password plus a new one twice. The email is not in the database: it is the one typed at log in or sign-up and is kept only in this browser (`kl-email` in localStorage, next to `kl-acct`). A saved login without `kl-email` (from before this existed) is dropped so the person logs in once more.
- Screens when logged out: Log in (email and password, then "Forgot your password?" and a "Sign up" link below it) and Sign up (name, email, password of 8+ characters, with a "Log in" link). A saved login is dropped if the account was removed or an admin reset its password.
- Passwords are a lock screen, not server security. Each is stored only as a salted PBKDF2-SHA-256 hash (200,000 rounds, email mixed into the input) in `logins/{id}` (`salt`, `hash`, `iter`, `setAt`). Never store a plaintext password. Because there is no server, `logins` must be readable by every signed-in viewer to check a login, and any Contributor can overwrite any record. Anyone with access to the data can attempt offline password guessing or tamper with other people's records. Share the site only with people you trust. Five wrong tries lock the form for 30 seconds.
- Forgot password: an admin (or super admin) clicks "Reset password" on the Users page, which sets `roles/{id}.pwReset`. The person enters their email on the Log in screen and is asked to choose a new password (no old one needed); the flag clears when `members/{id}.pwSetAt` is newer. Until then anyone who knows that email can claim the account. The site owner (Claude `isOwner()`) also sees "Reset password for this email" on the Log in screen, as recovery if the owner account is locked out. There is no email reset, because the site cannot send email, and emails are not verified.

## Data model (db collections)

- `sessions/{id}`: `title`, `date` (YYYY-MM-DD), `start` (HH:MM), `duration` (minutes), `court`, `venue`, `level`, `format`, `capacity`, `hostId` (an account id), `hostName`, `createdAt`. A session is deleted once its end time (start + duration, in the viewer's local time) passes: any signed-in viewer with write access deletes it on load or within 15 seconds (`purgeEnded` / `clockTick`). Nothing keeps a history of past sessions.
- `members/{id}`: `name`, `createdAt`, `pwSetAt` (the account profile, written at sign-up).
- `logins/{id}`: the password hash, described above.
- No email is stored anywhere. The Users page lists members by name. Do not add a plaintext email field without a way to keep it private.
- `roles/{id}`: `role`, `suspended?`, `owner?`, `pwReset?`, `by`, `at` (written by managers).
- `signups/{id}`: `joined` as `{ sessionId: joinTimestamp }`; the roster and waitlist order come from these timestamps.
- `config/booking`: `hours` (array of start hours, 0 to 23), `rates` (array of `{ from, to, price }`, hours 0 to 24) and `courts` (array of `{ name, venue }`). Missing or invalid values fall back to `DEFAULT_BOOKING`.
- `bookings/{date}_{venue}_{court}_{hour}` (no venue part when there are no venues): `date`, `venue` (empty when no venues), `court`, `hour` (start hour), `by` (account id), `byName`, `ref` (shared by every hour in one booking), `price`, `at`. The document id is unique to the slot, and a booking claims each slot with a short lease (`acquire`) then checks nobody owns it before writing; if any slot in the booking is taken, the slots already claimed are deleted again, so a booking is all or nothing. Lease-only documents with no `by` are ignored. Bookings saved before venues existed have no `venue` and are treated as belonging to the first venue. A booking is deleted once its hour has ended (`purgeEnded`).
- `config/roles`: `defs` as `{ roleKey: { label, perms } }` for the role access table.
- `config/options`: `levels`, `formats`, `courts`, `venues` (arrays of text). An older `durations` key may still be stored; it is ignored. Any key that is missing falls back to `DEFAULT_OPTIONS`.
- The older collections `accounts`, `players`, `contacts` and `data/users/*` (keyed by Claude sign-in, from before email accounts) are no longer read. Their docs can be deleted.

## Roles and permissions

- Built-in roles: super admin (always everything), admin, staff, player. Super admin can add custom roles.
- Features: view, join, roster, host, edit, remove, people, options, moveplayers, book, bookconfig, managebookings, viewbookers. Defaults are in `DEFAULTS` in the script. `people` opens the Users page (`renderUsers`): overview tiles, member search, role changes, Reset password, pause access, and Remove (super admin only; deletes that account's members, roles, signups and logins docs).
- Super admin: the first account the site owner (Claude `isOwner()`) signs up with becomes super admin (`roles/{id}`: `role: super_admin, owner: true`) when no super admin exists yet. Later accounts, including ones the owner makes while testing, start as players, so the owner can test other roles by creating accounts and logging in as them.
- Role checks are enforced by the page, not the server. Someone with Contributor access to the artifact could bypass them. Hard limits come from the Share menu levels.
